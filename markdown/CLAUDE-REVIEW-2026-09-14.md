## ข้อค้นพบที่ควรแก้

### 1. [P2] ช่องเปิดคิวเขียนว่าเวลาไทย แต่แปลงด้วยเขตเวลาของเครื่อง

ตำแหน่ง: [Profile.tsx:244](../src/pages/Profile.tsx#L244)

`datetime-local` ไม่มีเขตเวลา แต่ใช้ `new Date(when).toISOString()` จึงตีความค่าที่กรอกตามเครื่องผู้ใช้ ขณะที่คำอธิบายและรายการคิวระบุเวลาไทย

ยืนยันด้วยเบราว์เซอร์ timezone UTC: กรอก `2026-10-01T10:00` แล้วส่ง `2026-10-01T10:00:00.000Z` แทนค่าที่ควรเป็น `2026-10-01T03:00:00.000Z` หากหมายถึง 10:00 เวลาไทย ทำให้เวลาที่เปิดจริงกลายเป็น 17:00 ไทย เมนเทอร์ที่อยู่ต่างประเทศหรือเครื่องตั้ง timezone ผิดจะเปิดคิวผิดโดยไม่มีคำเตือน

แนวทางแก้: แปลงวันที่และเวลาที่กรอกโดยระบุ Asia/Bangkok หรือ offset +07:00 อย่างชัดเจน และทดสอบ browser timezone อย่างน้อย Bangkok/UTC/อีกหนึ่งเขตเวลา

### 2. [P2] เมนเทอร์ไม่เห็นข้อความแนะนำทีมก่อนรับคำขอ

ตำแหน่ง: [Profile.tsx:217](../src/pages/Profile.tsx#L217)

API ส่ง `booking.context` มาแล้ว แต่รายการนัดแสดงเพียงชื่อทีม ชื่องาน เวลา และสถานะ ไม่แสดงข้อความที่ทีมกรอกว่าอยากให้ช่วยอะไร และไม่มีหน้ารายละเอียดคำขอก่อนรับ เมนเทอร์จึงต้องตัดสินใจรับ/ปฏิเสธโดยไม่เห็นโจทย์ ซึ่งอาจเพิ่งเห็นเมื่อรับแล้วเปิดแชต

ยืนยันด้วยข้อมูลจำลองใน browser: ใส่ข้อความเฉพาะลง `booking.context` แล้วค้นหาในหน้าพบ 0 จุด ขณะมีปุ่มรับคำขอ

แนวทางแก้: แสดงข้อความแนะนำทีมและข้อมูลผู้ขอที่เหมาะสมข้างปุ่มตอบคำขอ รักษาบรรทัดและจัดการข้อความยาว พร้อมตรวจ mobile

### 3. [P2] หน้าจองเปิดฟอร์มแม้ผลจับคู่เป็น null

ตำแหน่ง: [MentorProfile.tsx:116](../src/pages/MentorProfile.tsx#L116)

API โปรไฟล์สามารถส่งข้อมูลเมนเทอร์พร้อม `match: null` ได้เมื่อเมนเทอร์ไม่ตรงกับงานหรือเลือกไม่รับงานนั้น แต่ UI ตรวจเพียงมีงาน มีคิว และเข้าสู่ระบบแล้ว จึงยังให้กรอกชื่อทีม ข้อความ และเลือกเวลา ก่อนถูกเซิร์ฟเวอร์ปฏิเสธตอนส่ง

ยืนยันด้วย browser ที่จำลอง response มี competition + slots + `match: null`: ฟอร์มจองยังแสดง ผลกระทบคือผู้ใช้เสียเวลากรอกและสับสน ไม่ใช่ช่องโหว่ข้ามสิทธิ์ เพราะ API `/bookings` ยังตรวจ eligibility

แนวทางแก้: แสดงข้อความไม่พร้อมช่วยงานนี้เมื่อไม่มี match พร้อมลิงก์กลับไปเลือกเมนเทอร์ และคงการตรวจที่เซิร์ฟเวอร์สำหรับกรณีข้อมูลเปลี่ยนหลังเปิดหน้า

### 4. [P2] ห้องแชตยังไม่แสดงรายละเอียดนัดที่ปักไว้ตามแผน

ตำแหน่ง: [Chats.tsx:89](../src/pages/Chats.tsx#L89), [chat.ts:61](../server/routes/chat.ts#L61)

ส่วนปักหมุดแสดงเฉพาะ `room.context` ส่วน API ห้องคืน room/members/invites โดยไม่มีข้อมูล bookings/slots จึงไม่เห็นวันเวลา สถานะ หรือรายการนัดในห้อง เมื่อจองรอบใหม่แล้วใช้ห้องเดิม context ยังเป็นโจทย์จากการสร้างห้องครั้งแรก ทำให้สมาชิกทีมที่ไม่ได้เป็นเจ้าของหรือเมนเทอร์ไม่มีทางอ่านเวลานัดผ่านหน้าโปรไฟล์ของตน

หลักฐานข้อนี้มาจากการอ่านโค้ด ไม่ได้สร้างกรณีจองรอบสองเพิ่มเติมใน browser

แนวทางแก้: ส่งข้อมูลนัดของห้องที่ผู้ใช้เป็นสมาชิก แสดงนัดถัดไป/สถานะ/เวลาไทยและบริบทของนัดนั้น โดยรักษาประวัตินัดเดิม ไม่เขียนทับข้อความเก่า

ระหว่างรันแบบ parallel พบ API log `23503` ที่ `mentorInfo` ใน [journey.ts:45](../server/routes/journey.ts#L45): การบันทึก `mentor_match_audit` ชนกับการลบเมนเทอร์ทดสอบจากอีก test จน foreign key ไม่พบ mentor แม้ test suite จบผ่านทั้งหมด ยังไม่ยืนยันว่าเกิดในเส้นทางใช้งาน Production ควรแยกการล้าง fixture กับ request ที่ยังทำงาน และทบทวนว่าการอ่านรายการแนะนำจำเป็นต้องล้มทั้งคำขอเมื่อบันทึก audit ไม่ได้หรือไม่

## ช่องว่างการทดสอบที่ยังเหลือ

- ยังไม่พบ test ที่ทดสอบขอคิวเดียวกันพร้อมกันหลายทีมแล้วสำเร็จเพียงหนึ่งทีม
- ยังไม่พบ test การหมดอายุของ **booking** เมื่อครบ 24 ชั่วโมง/ถึงเวลาเริ่ม และการปล่อยคิวให้จองใหม่; test ชื่อ expired ที่มีอยู่ตรวจ **คำเชิญแชต**
- ยังไม่พบ test เปิดคิวทับซ้อน รับนัดชนกัน และยกเลิกแล้วขอคิวใหม่
- ยังไม่พบ unit test ตารางคะแนนจับคู่ครบทุกแหล่งคะแนน การปิดหมวด และลำดับ tie-break
- ไม่ได้รัน full suite ในรอบนี้ ไม่ได้ยืนยัน Google จริงผ่าน provider หรือ deployment/migration บน Production

แนะนำแก้ข้อ 1–4 และเติม regression tests ของการจองก่อนถือว่าเส้นทางใหม่นี้พร้อมครบตามแผน ส่วนระบบเงิน/คืนเงินยังเป็นงานที่พักไว้ ไม่ใช่งานที่ Claude ส่งมอบใน commit นี้
