## 1. Rising Star

### สิ่งที่ตัดสินแล้ว

- ชื่อระบบ **Rising Star** ราคา **99 บาท**
- จ่ายผ่าน **Stripe** (Billing, Tax)
- โค้ดส่วนลด `RisingStar` → เหลือ **39 บาท** · `Tester001` → **ฟรี**
- **Hall of Fame** แถบบนสุด แสดงเมนเทอร์ที่มีคนปรึกษามากที่สุด
  - ตรงกลาง ใหญ่สุด: **เดือนนี้**
  - ซ้าย: **เดือนที่แล้ว**
  - ขวา: **สองเดือนก่อน**
  - แต่ละเดือนมีอันดับ 1 ใหญ่สุด แล้วเล็กลงเป็นอันดับ 2 และ 3
- เมนเทอร์ที่**ไม่ได้สมัคร** อยู่ต่ำกว่าคนที่สมัคร และ**ไม่มีการจัดอันดับ**

### คำถามที่ยังค้าง

| # | คำถาม | ทำไมต้องรู้ |
|---|---|---|
| 1 | 99 บาท **ต่อเดือน**ใช่ไหม | ตั้ง Price ใน Stripe เป็นรายเดือนหรือรายปี |
| 2 | **จด VAT แล้วหรือยัง** / 99 บาทรวม VAT ไหม | ถ้าเปิด Stripe Tax โดยไม่มีการลงทะเบียน Stripe จะไม่เก็บภาษีเลยทั้งที่ดูเหมือนเปิดอยู่ — ความผิดพลาดที่ Stripe ระบุว่าเจอบ่อยที่สุด |
| 3 | `RisingStar` ลด**ตลอดไป**หรือ**เดือนแรก** ใช้ได้กี่คน | ตั้ง `duration` และ `max_redemptions` ของคูปอง |
| 4 | `Tester001` ฟรี**กี่เดือน** จำกัดกี่ครั้ง | ถ้าไม่จำกัด โค้ดหลุดออกไปใครก็ใช้ฟรีได้ตลอด |
| 5 | "คนปรึกษามากที่สุด" นับจากอะไร | แนะนำ: นัดที่**ยืนยันแล้วและพ้นเวลานัดแล้ว**ในเดือนนั้น ถ้านับตอนกดจอง ปั่นอันดับได้ด้วยการจองแล้วยกเลิก |
| 6 | หมดอายุ subscription แล้ว อันดับในเดือนที่ผ่านมายังโชว์ไหม | Hall of Fame เดือนก่อน ๆ เป็นประวัติ ควรคงไว้ไหม |

### แผน backend (เลื่อนไว้ — บันทึกไว้ไม่ให้ต้องหาใหม่)

จากแนวปฏิบัติของ Stripe (skill `stripe-best-practices`, API `2026-08-26.dahlia`):

- ใช้ **Sandbox แยก** สำหรับพัฒนา ไม่ใช้ Test mode รวมของบัญชี
- ใช้ **Restricted key (`rk_…`)** ไม่ใช้ Secret key ใส่ใน `.env.local` เท่านั้น ห้ามวางในแชต
- Subscription ใช้ **Billing API + Checkout Sessions**
- **Webhook บังคับ** — เปิดสิทธิ์ Rising Star จาก webhook เท่านั้น ไม่ใช่จากหน้า "จ่ายสำเร็จ"
- ไม่ส่ง `payment_method_types` ให้ Stripe เลือกวิธีจ่ายเอง (จะได้ PromptPay ถ้าเปิดใน Dashboard)
- ใช้ `StripeClient` แบบ instance ไม่ใช้ `stripe.api_key` แบบเก่า
- เปิด `automatic_tax` **เฉพาะเมื่อ**ยืนยันการลงทะเบียน VAT แล้ว (คำถามข้อ 2)
- โค้ดจ่ายเงินทั้งหมดส่ง Astra (`security-reviewer`) รีวิวก่อน merge

ปลั๊กอิน Stripe ติดตั้งแล้ว (scope: project) และเชื่อมบัญชีผ่าน `/mcp` แล้ว ขั้นถัดไปคือเรียก `stripe_implementation_planner` ด้วยบริบทด้านล่าง:

> แพลตฟอร์มเว็บภาษาไทย เมนเทอร์สมัคร subscription รายเดือน "Rising Star" 99 บาท ผ่าน Stripe Checkout, คูปอง RisingStar → 39 บาท, Tester001 → ฟรี, ต้องการ Billing + Tax, stack: React + Hono (Node) + Postgres (Neon) บน Vercel

## 4. การลงงานแข่ง

1. **ผู้ใช้ขอเพิ่ม** — ผู้ใช้หางานแข่งมาแล้วส่งคำขอเข้าระบบ → แอดมินอนุมัติ
   - ตอนส่งเลือกได้ว่า**จะโปรโมทให้ขึ้นด้านบนไหม** ถ้าใช่ต้องจ่าย
2. **เจ้าของงานมาลงเอง** — วางแผนไว้สำหรับอนาคต ยังไม่ทำ

คำถาม: การโปรโมทงานแข่งใช้ Rising Star ตัวเดียวกัน หรือเป็นแพ็กเกจแยก (ซึ่งจะทับกับเรื่องที่ 2 ที่พักไว้)

ของเดิมที่ใช้ต่อได้: คิวตรวจใบลงงานของแอดมิน (`/admin/competitions`) มีขั้นจัดประเภทก่อนเผยแพร่แล้ว

## 5. ใบสมัครเมนเทอร์ + อีเมลแจ้งเตือน

- เก็บรายละเอียดการสมัครให้ครบ — ของที่ยังขาดตาม [NEXT-STEPS.md](NEXT-STEPS.md): อัปโหลดหลักฐานจริง (ตอนนี้บันทึกแค่ชื่อไฟล์), หน้าติดตามสถานะที่ผู้สมัครส่งข้อมูลเพิ่มได้
- อีเมลแจ้งเตือน — ระบบส่งผ่าน Resend มีอยู่แล้ว (`server/lib/email.ts`) แต่**ส่งถึงคนนอกไม่ได้จนกว่าจะมีโดเมนของตัวเอง**ไปยืนยันกับ Resend

## ลำดับการทำงาน (ตาม workflow ดีไซน์)

1. **design-lead** เสนอ 3 ทิศทางของ Rising Star (Hall of Fame + รายชื่อเมนเทอร์ที่จัดอันดับ + การ์ดชวนสมัคร) → **ผู้ใช้เลือก 1**
2. **design-system** ปรับ tokens/components ตามทิศทางที่เลือก → **ผู้ใช้ดูก่อนทำหน้าจริง**
3. **ui-builder** ทำหน้าแรก → design-critic → **ผู้ใช้ยืนยันสไตล์**
4. ทำหน้าที่เหลือ: ติดต่อแอดมิน, ขอเพิ่มงานแข่ง + ตัวเลือกโปรโมท, ใบสมัครเมนเทอร์
5. Astra (`e2e-tester`) ทดสอบเว็บจริงหลังผ่าน critic
6. backend Stripe เมื่อคำถามข้อ 1–4 มีคำตอบ
